# Audit Signal Urbain Togo — 2026-06-10

Audit du backend (NestJS/Prisma), du dashboard (React) et de l'application mobile (Expo/React Native). Objectif : sécurité, design/UX, fonctionnalités manquantes.

---

## 1. SÉCURITÉ — API (apps/api)

### CRITIQUE

**1.1 — IDOR : un AGENT/ADMIN peut modifier les incidents de N'IMPORTE QUELLE commune**
- `apps/api/src/incidents/incidents.service.ts:148-153`
- Le commentaire dans le code dit explicitement : *"Un AGENT ne peut modifier que sa commune (vérification simplifiée — à compléter avec communeId de l'agent)"* — **ce n'est pas implémenté**.
- `PATCH /incidents/:id` (changement de statut, priorité, assignation) fonctionne pour n'importe quel incident, peu importe la commune de l'agent.
- **Fix** : avant les `updates`, charger `agentCommuneId` (déjà dispo via `@CurrentUser`) et vérifier `agentRole === SUPER_ADMIN || incident.communeId === agentCommuneId`, sinon `ForbiddenException`.
- **Risque** : un agent malveillant ou compromis d'une commune peut clôturer/réassigner les incidents d'une autre commune.

**1.2 — Secrets dans `.env`**
- `apps/api/.env` contient JWT secrets, mot de passe DB, clé Cloudinary en clair.
- Le fichier est gitignoré (bon), mais comme il est question de sécurité globale : si ces valeurs sont des valeurs de DEV par défaut copiées en PROD (à vérifier sur Render), il faut les régénérer. Pas d'action immédiate si les vraies valeurs prod sont uniquement dans les variables d'env Render.

### HAUTE

**1.3 — IDOR : `PATCH /users/agents/:id` sans vérification de commune**
- `apps/api/src/users/users.controller.ts:65-72`
- Un ADMIN de la commune A peut modifier (rôle, commune, statut actif) un agent de la commune B — y compris le promouvoir SUPER_ADMIN si `role` n'est pas filtré côté validation.
- **Fix** : vérifier `targetAgent.communeId === admin.communeId` (sauf SUPER_ADMIN), et interdire `role: SUPER_ADMIN` dans ce endpoint réservé aux ADMIN.

**1.4 — IDOR : `GET /stats/commune/:id` accessible à tout AGENT**
- `apps/api/src/stats/stats.controller.ts:24-27`
- N'importe quel agent peut consulter les statistiques de n'importe quelle commune en changeant l'`:id`.
- **Fix** : si `role !== SUPER_ADMIN`, forcer `id = currentUser.communeId` et ignorer le paramètre.

**1.5 — `changePhone` sans DTO/validation**
- `apps/api/src/auth/auth.controller.ts:46`
- Body `{ newPhone, code }` non typé/validé par `class-validator`.
- **Fix** : créer un `ChangePhoneDto` avec `@Matches(/^\+228...$/)`.

### MOYENNE

**1.6** — `CreateIncidentDto` / `UpdateIncidentDto` / `ListIncidentsDto` sont des `interface` TypeScript, pas des classes `class-validator` (`apps/api/src/incidents/incidents.service.ts:7-37`). Si jamais utilisées directement comme type de `@Body()`, la validation globale ne s'applique pas vraiment à leur contenu.

**1.7** — `AuditLog` (schema.prisma) n'est jamais peuplé — aucune traçabilité des actions admin (changement de statut, suppression d'utilisateur, changement de rôle).

### Vérifié et OK
- Upload de photos : vérifie bien `incident.reporterId === userId`, valide type/taille (uploads.service.ts).
- Pas de `console.log`/erreurs Prisma brutes restantes ailleurs que ce qui a déjà été corrigé.
- Throttling présent sur `/auth/request-otp`.

## 2. DASHBOARD (apps/dashboard/src/App.tsx)

### Priorité HAUTE
- **Confirmations destructives via `confirm()` natif** (suppression agent ~1088, suppression commune ~1914, etc.) — UX pauvre, pas de contexte sur les dépendances. → Remplacer par des Modals avec détails (ex. "Cet agent a 3 incidents en cours").
- **Pas de pagination** sur Incidents/Utilisateurs/Citoyens (tout chargé d'un coup, limite 100). Risque de lenteur si une commune dépasse cette taille.
- **Export CSV absent** — un outil de gestion municipale en a presque toujours besoin (incidents, utilisateurs).
- **Table incidents non responsive** (grid colonnes fixes) — inutilisable sur petit écran/tablette portrait.

### Priorité MOYENNE
- Styles dupliqués (`sel`, `inp`, `btn` réécrits à plusieurs endroits) → factoriser dans un fichier `theme.ts`/constantes partagées.
- Accessibilité : `<select>`/`<input>` sans `<label>`, `outline: none` global empêche la navigation clavier, icônes sans `aria-label`.
- Statistiques limitées (pas de tendance temporelle, pas de SLA de résolution par agent).

### Déjà en place (bon)
- Demandes de changement de commune (onglet "Demandes") fonctionnelles.
- Suppression d'agent avec détection des incidents assignés + réassignation forcée.
- `useMemo`/`useCallback` utilisés correctement pour le filtrage.

## 3. MOBILE (apps/mobile)

### Priorité HAUTE
- **Couleurs/thème dupliqués dans 8 fichiers** (`COLORS` redéfini partout) → centraliser dans `lib/theme.ts`.
- **Fallback GPS silencieux** : si la localisation échoue, coordonnées par défaut codées en dur (`(6.1375, 1.2123)`, Lomé) sans avertir l'utilisateur — un signalement peut être géolocalisé au mauvais endroit sans que personne ne le sache. → Afficher une alerte et exiger une adresse manuelle si le GPS échoue.
- **Pas de feedback visuel pendant l'upload de photo** (spinner/progress) dans `report.tsx`.
- **Zones tactiles trop petites** (<44x44) sur plusieurs boutons (catégories, chips de commune, upvote) — accessibilité tactile.
- **Aucun `accessibilityLabel`** sur les icônes/boutons — inutilisable avec un lecteur d'écran.
- **Pas de message de justification** pour les permissions caméra/localisation (`permissionMessage` manquant) — recommandé par Apple/Google.

### Priorité MOYENNE
- Aucun mode hors-ligne : un signalement en cours est perdu si le réseau coupe pendant l'envoi (pas de file d'attente locale).
- Notifications push : pas de listener "notification cliquée → ouvrir l'incident correspondant".
- Pas de timeline "qui/quand" pour les changements de statut d'un incident côté mobile.

### Vérifié et OK
- Token stocké via `expo-secure-store` (chiffré) — correct.
- Permissions demandées au moment de l'usage (pas au démarrage) — bonne pratique UX.
- États vides/chargement bien gérés sur la plupart des écrans.
